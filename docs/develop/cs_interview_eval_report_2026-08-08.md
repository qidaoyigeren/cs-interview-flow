## Runner 结果

- Python、Go、JavaScript 正确代码均通过。
- 候选程序网络访问被阻断。
- 连续两轮 smoke 均通过；第二轮典型耗时为 Python 118 ms、Go 34 ms、JavaScript 66 ms、网络隔离用例 66 ms。
- 编译器与候选程序分开施加资源策略；Go 标准库缓存预热，避免首次编译超时。

## 本轮修复的问题

1. 修复简历上传时嵌套数据库事务/连接上下文冲突。
2. 修复 1 分具体错误回答无法触发追问；0 分空白、4 分满分和达到上限时仍禁止追问。
3. 统一 Judge 评分：0 分仅用于空白、拒答、无关或没有技术尝试，相关但主要错误的回答为 1 分。
4. 题目模型首次返回不完整 JSON 时改为继续受控重试，而不是直接终止 session。
5. `ai_backend` 成为一等岗位，加入 RAG、Agent、应用评测和算法能力。
6. `algorithm.core` 使用 `role=cs_general` 的共享算法库，避免按岗位复制同题。
7. `excluded_topics` 进入面试计划时硬排除，`focus_topics` 获得确定性优先级。
8. 修复 Runner 的编译期内存、进程、文件大小、只执行 tmpfs、cgroup PID 和 Go/Node 虚拟地址空间问题。

## 上线前差距（按优先级）

### P0

1. **交互延迟**：单步 16–52 秒不符合真实面试对话体验。需要更快模型或分级模型、流式状态、检索与上下文准备并行、缓存、严格超时与降级，并建立首 token/P50/P95 SLA。
2. **评测可信度**：建立至少 500 条人工标注查询，包含改写、跨主题干扰、困难负样本、无答案和 prompt injection；对 Recall、无证据拒答、Judge 一致率和追问合理率给出置信区间。
3. **知识治理**：每篇题目需要技术审核、来源/许可审核、版本、过期时间、下架与申诉流程；100 篇开发语料不能直接充当生产题库。
4. **长会话 E2E**：补 8–12 题完整面试，覆盖难度升降、连续弱答、追问达到 N、题目去重、代码题、终止、重放、并发与失败恢复。

### P1

1. 在标注集上评估并启用 reranker，联合调优相似度阈值与 top-k；当前实测 `rerank_id` 为空。
2. 入库工具目前串行处理 100 篇约 287 秒，需要受控并发、断点续传、失败重试和进度持久化。
3. Runner 当前单并发，需队列、背压、水平扩容、压测和租户配额；Go/Node 的请求内存是堆预算，真正硬边界来自 384 MiB 容器 cgroup。
4. 增加多模型回归，避免简历抽取、Judge 分数和追问策略只对当前模型校准。

### P2

1. 增加运营后台：题目审核、坏题反馈、命中证据、会话失败原因、成本与延迟看板。
2. 增加数据保留、简历删除、脱敏审计、用户导出和版权下架机制。
3. 为每个岗位补足 beginner/medium/advanced 的均衡覆盖，并按公司、轮次、年份和技术版本维护时效性。
